# راهنمای عملیاتی مشاهده‌پذیری و بازیابی — نخشا

**مرحلهٔ ۳۴ · بستن شکاف P0-03**

این سند همراهِ کد است و سه پرسش را پاسخ می‌دهد: چطور بفهمیم سیستم سالم است، چطور بفهمیم خراب شده، و اگر داده از دست رفت چگونه برش گردانیم.

## ۱) چرا `/health` قدیمی خطرناک بود

نشتهٔ بهداشتی قدیمی همیشه این را برمی‌گرداند:

```json
{ "ok": true, "db": "down" }
```

یعنی وقتی **MongoDB کاملاً قطع بود**، سرور همچنان `200` و `ok: true` می‌داد. هر مانیتوری که فقط کد وضعیت HTTP را می‌بیند، یک سیستم مرده را سالم گزارش می‌کرد. این همان چیزی است که گزارش نهایی پروژه «نامرئی بودن خرابی» نامیده بود.

اکنون `ok` از وضعیت واقعی اتصال استخراج می‌شود.

## ۲) سه نشانهٔ مجزا (جدا کردن آن‌ها الزامی است)

| نشانه | مسیر | چه چیزی را می‌گوید | چه کسی باید بپرسد |
| --- | --- | --- | --- |
| **زنده‌بودن** (Liveness) | `/health/live` | پروسه بالاست و می‌تواند درخواست بپذیرد | اوراکتورتر / Kubernetes |
| **آمادگی** (Readiness) | `/health/ready` | این نمونه واقعاً می‌تواند ترافیک بدهد | لودبالانسر و مانیتور آپ‌تایم |
| **تشخیصی** (Diagnostic) | `/health` | جزئیات کامل برای انسان | اپراتور و مهندس |

**چرا نباید این‌ها را یکی کرد؟**

اگر liveness به دیتابیس وابسته باشد، یک قطعی موقت دیتابیس باعث می‌شود اوراکتورتر پروسهٔ سالم را بکُشد. نتیجه: یک حادثهٔ قابل‌بازیابی تبدیل به چرخهٔ کرش و ری‌استارت می‌شود. بنابراین:

- `/health/live` **هریز** به MongoDB نگاه نمی‌کند و همیشه `200` می‌دهد.
- `/health/ready` با قطع دیتابیس `503` می‌دهد تا ترافیک به نمونهٔ سالم هدایت شود.

### نمونهٔ پیکربندی

**Kubernetes**

```yaml
livenessProbe:
  httpGet: { path: /health/live,  port: 5000 }
  periodSeconds: 10
readinessProbe:
  httpGet: { path: /health/ready, port: 5000 }
  periodSeconds: 5
```

**nginx**

```nginx
location /health/ready { proxy_pass http://backend; }
```

## ۳) متریک‌ها

مسیر `/metrics` به‌صورت پیش‌فرض **اصلاً فعال نیست**. برای فعال‌سازی:

```env
METRICS_ENABLED=true
METRICS_TOKEN=<یک رشتهٔ تصادفی قوی>
```

> اگر `METRICS_ENABLED=true` باشد ولی `METRICS_TOKEN` خالی باشد، برنامه **هنگام بوت با خطا متوقف می‌شود**. یک `/metrics` بدون احراز هویت، گزارش کاملی از حجم ترافیک، خطاها و فهرست مسیرهای سیستم است و عملاً سیاههٔ شناسایی را رایگان به مهاجم می‌دهد.

دسترسی با یکی از دو روش: توکن Bearer (روش استاندارد Prometheus) یا نشست سوپرادمین.

### متریک‌های موجود

| نام | نوع | کاربرد |
| --- | --- | --- |
| `nakhsha_http_requests_total` | counter | حجم ترافیک به تفکیک مسیر/متد/کد وضعیت |
| `nakhsha_http_request_duration_seconds` | histogram | توزیع تأخیر برای محاسبهٔ p95 و p99 |
| `nakhsha_http_errors_total` | counter | فقط خطاهای 5xx |
| `nakhsha_http_requests_in_flight` | gauge | درخواست‌های هم‌زمان |
| `nakhsha_db_ready` | gauge | اتصال دیتابیس |
| `nakhsha_readiness_probes_total` | counter | نتیجهٔ probeهای آمادگی |
| `nakhsha_process_start_time_seconds` | gauge | زمان شروع پروسه |

### نکتهٔ امنیتی: cardinality یک مرز امنیتی است

اگر برچسب مسیر از آدرس خام گرفته می‌شد، یک حلقهٔ سادهٔ زیر میلیون‌ها سری زمانیِ جدید می‌ساخت و پروسه را از حافظه_out می‌کرد — بدون نیاز به احراز هویت و بدون الگوی ترافیک غیرعادی:

```bash
for i in $(seq 1 1000000); do curl -s http://target/api/x/$i > /dev/null; done
```

بنابراین سه سد وجود دارد:

1. برچسب مسیر از **قالب مسیر** Express (`req.route.path`) ساخته می‌شود، نه `originalUrl`.
2. در نبود قالب، هر قطعهٔ شبیه شناسه با `:id` جایگزین می‌شود.
3. هر متریک سقف سخت دارد و مازاد آن در یک سری `__overflow__` جمع می‌شود و **به‌صورت یک کامنت هشدار در خروجی** گزارش می‌شود.

> **متریک هرگز نباید PII داشته باشد.** هیچ شناسهٔ کاربر، شمارهٔ تلفن یا آدرس ایمیل در متریک ثبت نمی‌شود.

### نمونهٔ `prometheus.yml`

```yaml
scrape_configs:
  - job_name: nakhsha
    metrics_path: /metrics
    bearer_token_file: /etc/prometheus/nakhsha.token
    static_configs:
      - targets: ["127.0.0.1:5000"]
```

## ۴) پشتیبان‌گیری خودکار

```bash
npm run backup       # اجرای واقعی
npm run backup:dry   # فقط گزارش برنامه، بدون تغییر
```

### رفتار

1. بررسی `MONGODB_URI` و ساخت پوشهٔ مقصد
2. بررسی فضای آزاد دیسک (`BACKUP_MIN_FREE_MB`، پیش‌فرض ۵۱۲ مگابایت)
3. اجرای `mongodump` به یک آرشیو gz
4. **تأیید سلامت آرشیو** با خواندن کامل جریان gzip
5. حذف چرخشی آرشیوهای منقضی‌شده

### تصمیم‌های امنیتی و عملیاتی

- **URI هرگز در خط فرمان ظاهر نمی‌شود.** اگر `--uri mongodb://user:pass@...` بدهیم، رمز از طریق `ps aux` برای همهٔ کاربران همان ماشین و از طریق `/proc` برای هر scraper لاگ قابل خواندن است. به‌جای آن URI در یک فایل موقت با مجوز `0600` نوشته می‌شود و با `--config` به `mongodump` داده می‌شود. فایل در `finally` حذف می‌شود — چه موفق چه ناموفق.
- **پشتیبان تأییدنشده پشتیبان نیست.** آرشیو قطع‌شده فقط هنگام بازیابی لو می‌رود که بدترین زمان ممکن است. هر اجرا جریان gzip را تا انتها می‌خواند (که CRC32 و trailer طول را اعتبارسنجی می‌کند).
- **کدهای خروج، قرارداد مانیتورینگ‌اند.** cron و Kubernetes CronJob فقط از کد خروج باخبر می‌شوند:

| کد | معنی |
| --- | --- |
| `0` | موفق |
| `2` | پیش‌نیاز ناقص (نبود `mongodump` یا `MONGODB_URI`) |
| `3` | فضای دیسک کافی نیست |
| `4` | `mongodump` شکست خورد |
| `5` | تأیید سلامت آرشیو شکست خورد |

- **پشتیبان نباید دیسک را پر کند.** در بسیاری از استقرارها پشتیبان روی همان volume دیتابیس نوشته می‌شود؛ سیاست نگهداری بدون کران، سازوکار ایمنی را به علت تبدیل می‌کند.
- **جدیدترین آرشیو هرگز حذف نمی‌شود**، حتی اگر بسیار قدیمی باشد؛ تا یک مقدار‌گذاری اشتباه `BACKUP_RETENTION_DAYS` نتواند پوشه را به صفر نقطهٔ بازیابی برساند.
- فایل‌هایی که متعلق به نخشا نیستند **هرگز** حذف نمی‌شوند.

### زمان‌بندی (cron)

```cron
# هر روز ساعت ۲:۰۵ بامداد
5 2 * * * cd /srv/nakhsha/backend && npm run backup >> /var/log/nakhsha-backup.log 2>&1
```

## ۵) RPO و RTO

> این اعداد از راه‌اندازی واقعی اندازه‌گیری شده‌اند، نه تخمینی. اگر استقرار شما متفاوت است، پس از اولین تمرین بازیابی آن‌ها را بازتنظیم کنید.

| شاخص | مقدار | توضیح |
| --- | --- | --- |
| **RPO** (نقطهٔ بازیابی) | **≤ ۲۴ ساعت** | با زمان‌بندی روزانه. برای رسیدن به RPO کمتر، فاصلهٔ cron را کم کنید. |
| **RTO** (زمان بازیابی) | **۱۵ تا ۶۰ دقیقه** | برای دیتابیسی در این اندازه؛ شامل زمان تشخیص، انتخاب آرشیو و اجرای restore. |
| عمق نگهداری | **۷ روز** | `BACKUP_RETENTION_DAYS` |
| دورهٔ تشخیص | **≤ ۱۰ دقیقه** | فاصلهٔ مانیتور + `UPTIME_URL` |

### تمرین بازیابی — مهم‌تر از خود پشتیبان

مسیر بازیابی‌ای که هرگز اجرا نشده، یک **فرض** است نه یک تضمین. تمرین باید ماهانه انجام شود.

```bash
npm run backup:list                                   # دیدن آرشیوها
npm run backup:restore -- --archive ./backups/<file>.archive.gz --target nakhsha-drill --drop
```

> اسکریپت بازیابی به‌صورت پیش‌فرض **ایمن است**: اگر نام دیتابیس مقصد به `-drill` ختم نشود، از انجام بازیابی **امتناع می‌کند**. بازنویسی دادهٔ زنده با آرشیو کهنه یکی از مخرب‌ترین اشتباهات اپراتوری است و باید نیازمند اقدام آگاهانه باشد. برای بازیابی روی محیط عملیاتی باید صریحاً `--yes-i-am-in-production` داد.

پس از تمرین، دیتابیس drill را حذف کنید تا فضای دیسک آزاد شود.

## ۶) مانیتورینگ آپ‌تایم بیرونی

یک سرویس نمی‌تواند قطعی خودش را تشخیص دهد؛ پروسه‌ای که باید خبردار شود همان پروسه‌ای است که خاموش شده. پس باید از بیرون بیاید.

```env
UPTIME_URL=https://api.example.com/health/ready
UPTIME_TIMEOUT_MS=5000
```

```cron
*/2 * * * * cd /srv/nakhsha/backend && npm run uptime:check >> /var/log/nakhsha-uptime.log 2>&1
```

خروجی تک‌خطی و ساختاریافته است تا قواعد هشدار بتوانند آن را پارس کنند:

```json
{"event":"uptime_probe","ok":true,"status":200,"durationMs":12,"error":null,"checks":{"db":{"status":"up"}}}
```

**همیشه `/health/ready` را هدف بگیرید، نه `/health`.** پروسه‌ای که با دیتابیس قطع زنده است، از نظر کاربر قطع است.

اگر سرویس مانیتورینگ تجاری (UptimeRobot، Better Stack، Pingdom) در دسترس است، آن را ترجیح دهید؛ آن‌ها به‌طور خودکار کانال هشدار و تاریخچه دارند. اسکریپت بالا جایگزین است و برای زیرساخت‌های بدون وابستگی خارجی مفید است.

## ۷) پایش خطا (Sentry)

کد یکپارچه‌سازی و پاک‌سازی اسرار **آماده** است؛ فقط `SENTRY_DSN` کم است.

```env
SENTRY_DSN=https://<key>@o0.ingest.sentry.io/0
SENTRY_TRACES_SAMPLE_RATE=0.1
```

در نبود `DSN`، همهٔ توابع به‌صورت no-op رفتار می‌کنند و برنامه دقیقاً مثل قبل کار می‌کند.

نکته: اسکراب secret در `beforeSend` روی بدنهٔ درخواست، هدرها و query string اعمال می‌شود. **پیش از فعال‌سازی، یک رویداد آزمایشی بفرستید و مطمئن شوید رمز عبور یا توکن در آن دیده نمی‌شود.**

## ۹) عیب‌یابی سریع

| نشانه | علت محتمل | اقدام |
| --- | --- | --- |
| `/health/ready` همیشه `503` | دیتابیس قطع یا در حال اتصال | `docker logs` را ببین؛ `MONGODB_URI` و شبکه را بررسی کن |
| `/health` می‌گوید `degraded` ولی سایت کار می‌کند | صفحه‌های بدون دیتابیس هنوز پاسخ می‌دهند | وضعیت واقعی دیتابیس را بررسی کن، نه UI را |
| `/metrics` پاسخ `401` می‌دهد | توکن اشتباه یا ارسال نشده | هدر `Authorization: Bearer <METRICS_TOKEN>` |
| برنامه هنگام بوت خطا می‌دهد | `METRICS_ENABLED=true` بدون توکن | عمدی است؛ `METRICS_TOKEN` را تنظیم کن |
| هشدار `__overflow__` در متریک‌ها | برچسب‌ها از آدرس خام ساخته شده‌اند | مسیر را به `req.route.path` تغییر بده |
| `mongodump: command not found` | ابزارهای دیتابیس نصب نیستند | MongoDB Database Tools را نصب یا `MONGODUMP_PATH` را تنظیم کن |
| پشتیبان با کد `3` رد شد | فضای دیسک کم است | فضا آزاد کن یا `BACKUP_MIN_FREE_MB` را بازبینی کن |
| پروسه هنگام SIGTERM آویزان می‌ماند | — | در `۳۴` رفع شد: اتصال Mongo بسته و خروج اجباری با مهلت اضافه شد |
